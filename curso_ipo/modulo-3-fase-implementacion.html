De la Especificación y Prototipos al Código Software

Naturaleza de la fase dentro de los ciclos interactivos de DCU

MPIu+a :: Pipeline-Phase-03

En el modelo de proceso MPIu+a, la fase de implementación no parte desde una hoja en blanco ni de conjeturas apresuradas. El trabajo sustancial de comprensión conceptual, modelado de tareas del usuario y diseño arquitectónico ha quedado plenamente consolidado en las etapas anteriores. Las actividades de esta fase pertenecen, mayoritariamente, al dominio riguroso de la Ingeniería del Software (codificación, arquitectura de módulos, integración y pruebas de integración).

No obstante, MPIu+a introduce un postulado crítico: la programación no es una caja negra aislada del usuario. Resulta indispensable continuar realizando evaluaciones constantes con prototipos software funcionales y versiones preliminares en las que participen directamente usuarios e implicados representativos (stakeholders).

Minimización de costes por cambio tardío

Aunque la fase de codificación consume habitualmente el mayor porcentaje de horas-persona del proyecto, aplicar de forma metódica el modelo MPIu+a reduce radicalmente la probabilidad de refactorizaciones estructurales provocadas por malinterpretaciones del problema.

Eje Curricular A

Codificación en el Modelo MPIu+a

Trazabilidad, preservación de especificaciones y gobernanza del código

Durante la escritura de código existe un riesgo silencioso pero crítico: la corrupción inadvertida del diseño por alteraciones casuales o «bienintencionadas». Pequeños cambios en espaciados, orden de tabulación, tiempos de respuesta o comportamiento de controles desarticulan los modelos mentales validados previamente en prototipado.

group_work
Coordinación Diseñadores ⇄ Programadores Establecimiento de canales unificados (Design Tokens, Storybook, contratos de interfaz) para anular discrepancias entre el prototipo validado y el componente implementado.
balance
Superación del Sesgo Técnico Los desarrolladores han sido tradicionalmente formados para optimizar el peso del binario y la velocidad de CPU, postergando la usabilidad, la ergonomía visual y los estados accesibles.
rule
Compromiso Estricto con el DCU Cualquier refactorización o alteración lógica que modifique la interacción debe someterse a validación con usuarios reales antes de consolidarse en producción.

Eje Curricular B

Accesibilidad en la Implementación

WAI-W3C, ética profesional y la tecnología de asistencia

La accesibilidad debe proyectarse desde la primera línea de código. Si se programa de manera secuencial y estructurada, el esfuerzo marginal añadido es prácticamente nulo; si se posterga como un parche cosmético final, el coste se multiplica exponencialmente.

gavel
Advertencia Ética: Las Trampas Sintácticas Es fácil «engañar» a validadores automáticos inyectando atributos aria-* o alt="" vacíos para obtener una puntuación 100%. La accesibilidad genuina requiere rigor ético hacia personas con necesidades reales.
flaky
La Falacia de la Equiparación Automática «Hacer un sistema accesible no lo convierte automáticamente en usable para personas con discapacidad». Se requiere evaluar cómo interactúan lectores de pantalla (JAWS/NVDA), pulsadores únicos y magnificadores.

Estándares WAI & WCAG 2.2 Cumplimiento verificado de los principios: Perceptible, Operable, Comprensible y Robusto a nivel semántico de marcado.

Concepto Didáctico #1

Prototipos de Alta Fidelidad Tempranos en Código

En MPIu+a, no se espera al ensamblaje del 100% del software. Se construyen «esqueletos interactivos» que conectan componentes clave para medir tiempos de respuesta percibidos y confirmar que el modelo mental del usuario se respeta en la tecnología real.

$ git checkout -b feature/user-task-flow-alpha
$ npm run build:interactive-skeleton

# 2. Test empírico con 5 usuarios representativos
$ ./mpiua-cli audit --users=representative --task="checkout_01"
✓ Flujo completado sin desbordamiento cognitivo
✓ Latencia percibida: 120ms (Cumple ISO 9241-11)
cancel Mala Práctica: Alteración Arbitraria de Dev

El desarrollador reemplaza un menú validado por conveniencia técnica de un framework, rompiendo la navegación:

<!-- Cambiado por el dev sin consultar al diseñador -->
<div onclick="doAction()" class="btn-custom">
  Aceptar operación
</div>
Riesgo: Pierde soporte de teclado (Tab/Enter), foco y accesibilidad semántica.
check_circle Solución MPIu+a: Preservación Semántica

Componente fiel a la especificación, accesible por teclado y con estado de carga predecible:

<button type="button" aria-busy="false" class="btn-primary">
  <span class="label">Aceptar operación</span>
</button>
Ventaja: Garantiza interacción nativa para cualquier tecnología de asistencia.
warning «Trampa» para el Auditor Automático

Etiquetas añadidas para burlar validadores que frustran al usuario de lector de pantalla:

<!-- Pasa tests automáticos con 100% pero es inútil -->
<img src="grafica.png" alt="imagen" />
<input type="text" aria-label="campo" />
El lector verbaliza: «Imagen. Campo». Cero contenido informativo real.
verified Rigor Ético en Código MPIu+a

Descripción substantiva y contextual que otorga autonomía real al usuario ciego o con baja visión:

<img src="grafica.png"
  alt="Gráfico de barras: tasa de errores reducida en un 64% tras DCU." />
<input type="email" id="user-email"
  aria-describedby="email-hint" required />
Resultado: Información equivalente y usabilidad plena para el usuario.
checklist_rtl Checklist Canónico Pre-Lanzamiento (Evaluación Heurística de Código)
Metodología Toni Granollers
1. Consistencia Visual y Operativa

Verificar que la terminología, ubicaciones de botones y comportamientos del cursor no difieren entre módulos implementados por distintos equipos.

2. Control y Libertad del Usuario

Comprobar que todas las transacciones críticas cuentan con confirmación previa y posibilidad real de «Deshacer» (Undo/Redo).

3. Mensajes de Error en Código

Eliminar códigos de excepción de base de datos (`SQLSTATE 23505`) y presentar textos orientados a la solución para el usuario.

Matriz de Diferenciación

Ingeniería de Software Tradicional vs. Fase de Implementación MPIu+a

Cómo transforma el DCU el trabajo de codificación del producto

Dimensión de Desarrollo Enfoque Tradicional / Cascada Enfoque MPIu+a (DCU)
Punto de inicio en código A menudo se programa desde especificaciones abstractas no testeadas. Se programa sobre prototipos validados empíricamente con usuarios.
Criterio de éxito del programador Cumplir requerimientos funcionales y optimizar CPU/RAM. Eficacia, eficiencia y satisfacción del usuario final + accesibilidad.
Tratamiento de la Accesibilidad Parche cosmético de última hora para cumplir auditorías normativas. Semántica nativa integrada desde la primera línea de código.
Gestión del cambio en código Decisiones unilaterales de desarrollo ante dificultades técnicas. Todo cambio en la interacción se revalida con usuarios e implicados.
Auditoría previa a puesta en producción Pruebas unitarias de software y tests de carga exclusivamente. Pruebas de software + Evaluación heurística formal de usabilidad.
